The Problem

Hybrid QA needs complete answers. Retrieval can’t guarantee that.

Real questions over mixed table–text corpora demand lists, counts, aggregates, and set differences — where missing even one evidence passage silently corrupts the answer. Existing retrieve-then-generate systems hit a wall.

Dense retrieval misses tail evidence

Top-k passage retrieval skips rare facts. For a query like "players who scored 30+ points", a single overlooked passage breaks the answer set.

Per-query LLM extraction is prohibitive

Running an LLM over all 45,000 passages at query time is slow and expensive — and still offers no completeness guarantee.

The Idea

Materialize text into tables offline. Then query like a database.

CODA reconceptualizes hybrid QA as query processing over a mixed relational–textual corpus. Text becomes tables once, up front. SQL handles the rest.

01 · OFFLINE

Text-to-Table Materialization

A three-stage pipeline turns linked passages into virtual relational tables, guided by source-table metadata.

  • Propositional atomization
  • Schema-guided mapping
  • Dynamic schema discovery
02 · PLANNING

Completeness-Aware DAG Planner

Decomposes NL queries into operator DAGs with per-leaf completeness contracts — exact vs. top-k — and routes via omission-risk cost.

  • Schema-aware decomposition
  • Exact / top-k contracts
  • Join-aware scheduling
03 · EXECUTION

Two-Tier Runtime with Self-Repair

Tier 1 runs SQL on materialized tables. Tier 2 falls back to bounded on-demand extraction — and feeds results back into the cache.

  • Sub-second Tier-1 SQL
  • Bounded Tier-2 fallback
  • Incremental cache repair
Architecture

One-time offline cost. Sub-second online answers.

The offline pipeline runs once per corpus. At query time, most answers never touch an LLM.

Tier 1 · Cached

SQL on Materialized Tables

DuckDB executes directly against validated virtual tables. Exact answers for aggregates, set ops, and complex joins.

~1s · 90%+ of queries
Tier 2 · Fallback

Bounded On-Demand Extraction

When a query touches unmaterialized attributes, SQL first narrows candidates (≤200), then an LLM extracts only those passages.

~30s · merged into cache
